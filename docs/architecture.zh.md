## 2. 三省六部旅游专署（部门设计）

复用 edict 的流水线模式与 OpenClaw 环境，全新定义「旅游专署」职责。现有 16 个 agent 全部在线，只需重写 SOUL.md + 装对口工具，无需新建 agent。

### 2.1 中枢四衙

| 衙门 | Agent | 旅游专署职责 | 输入 → 输出 |
|---|---|---|---|
| 太子 | taizi | 需求解析 | 表单原始数据 → 《行旅旨意》(结构化 brief：地点/天数/预算/风格/同行人画像/偏好/日期窗口)；缺关键信息时生成 1~2 个追问 |
| 中书省 | zhongshu | 方案草拟 | 六部产出文件 + 旨意 → 2~3 套候选方案（含每日行程、交通、住宿、预算分表、利弊） |
| 门下省 | menxia | 封驳审核 | 中书方案 → 准奏 / 打回清单（查：广告嫌疑、时效、行程逻辑矛盾、预算矛盾、数据缺失） |
| 尚书省 | shangshu | 执行调度 | 旨意 → 六部任务分派单 + 进度追踪（CLI 模式下由 Hermes 实际执行调度，尚书为监督角色） |

### 2.2 六部（旅游专署定位）

| 部 | Agent | 职责 | 关键产出 |
|---|---|---|---|
| 吏部 | libu_hr | 同行人画像策略 | 老人/小孩/情侣/朋友 → 节奏建议、住宿标准、交通方式、餐食禁忌 |
| 户部 | hubu | 预算核算 | 分项成本（交通/住宿/餐饮/门票/应急）+ 总账 + 价格区间 + 超支风险点 |
| 礼部 | libu | 攻略采集 | 景点/美食/小众玩法/穿搭建议/天气/文化礼仪（小红书优先，降级链见 §5） |
| 兵部 | bingbu | 交通调研 | 12306 车次时刻票价、航班参考、中转省钱经验贴、交通工具选择策略 |
| 工部 | gongbu | 地图测算 | 两点间路线时间距离、每日动线、景点间通勤、行程可行性验证（高德 API） |
| 刑部 | xingbu | 信息核验 | 真实性校验、广告识别、时效核验、溯源标签打标（✅实查 / 📊估算） |

### 2.3 职责边界（做判分离）

- **做**：六部采集/测算 → **判**：刑部独立核验 + 门下独立封驳
- 礼部说「XX 餐厅人均 80」→ 刑部必须核实来源，无法核实则标 📊估算
- 任何预算数字必须能追溯：来源 URL + 查询时间 + 实查/估算标签
- 🔴 **判的核心不是「LLM 写审核意见」，而是确定性 Python 校验函数**（依据：TravelPlanner 基准证明 GPT-4 纯生成行程的硬约束通过率 <1%，LLM 自查天然不可靠）：
  - 信息核验 = POI 存在性/营业时间/门票价格对照真实数据源
  - 预算核算 = 逐项累加（交通+住宿+餐饮+门票+应急）与预算上限比对，如 `total_cost <= 3000`
  - 路线测算 = 景点间距离矩阵 + 营业时间窗冲突 + 单日时长上限
  - LLM 角色退化为：①生成方案；②定向修复校验器报出的违规项（每轮只修一个问题，最多 N 轮）

## 3. 核心工作流（内测版 8 步流水线）

```
① 用户填表 → Hermes 校验表单
② 太子解析 → 《行旅旨意》brief + Planning Brief 确认卡（回显逐项理解）
    用户确认 / 修改 → 缺关键信息时 1~2 个追问（与确认卡合并为一轮）
③ 尚书分派 → 六部并行调研（每部一个 OpenClaw agent，输出独立文件）
    吏部/户部/礼部/兵部/工部 五部并行 → 刑部随后独立核验
    ⚠️ 采集产出物 = 结构化 JSON（POI列表/价格/营业时间/车次/酒店档位），
       禁止攻略散文（消灭幻觉价格的唯一办法是不让 LLM 编数据）
④ 刑部核验 → 确定性 Python 校验函数逐条验真 + 打溯源标签 → 核验报告
⑤ 中书草拟 → 只读「用户参数 + 采集JSON + 核验报告」组装 2~3 套方案
    禁止在无数据处自由发挥，缺失数据显式标注「待核实」
⑥ 门下封驳 → 确定性校验（预算累加/时间冲突/行程逻辑）+ 审核意见 → 打回清单（最多2轮）
⑦ Hermes 终审 → 渲染 HTML 方案页 → 交付
⑧ 用户修改意见 → 「迷你重跑」：只派受影响部门，从中书/封驳 checkpoint 恢复
```

                       │ 调用
┌──────────────────────▼──────────────────────────────┐
│  编排层：Hermes（中枢调度，我）                     │
│  太子解析 → 尚书分派 → openclaw agent CLI 逐部调用  │

## 5. 信息溯源机制（硬性要求）

每条进入方案的数据必须带三要素：

```
[📍来源: <URL 或站点名>] [🕐查询时间: 2026-08-14] [✅实查 | 📊估算 | ⚠️传闻]
```

- ✅实查：通过接口/页面实际查到当前数据
- 📊估算：基于同类数据的合理区间推断（如「淡季同档民宿 ¥200-300」）
- ⚠️传闻：仅见网友分享、无法复核（原则上不允许进入最终方案，除非用户要求收录）
- 前端渲染为小标签，点开可见来源链接

## 6. 多方案设计

| 方案档位 | 定位 | 默认生成条件 |
|---|---|---|
| 经济型 | 预算优先 | 用户给预算下限时必出 |
| 均衡型 | 性价比 | 默认必出 |
| 舒适型 | 体验优先 | 用户给预算上限或佛系风格时必出 |

每套方案含：路线地图（标记每日动线）、每日时间轴（时间-地点-交通-备注）、住宿建议、分项预算表+总账、利弊清单（优点/坑点/适合人群）。最后附三套对比表。
